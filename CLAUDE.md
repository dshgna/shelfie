# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Shelfie is a private, local-first home inventory app (household and personal-care items). Web app first (installable PWA), then iOS and Android via Capacitor from the same code.

## Decisions (do not revisit without asking)

- React + TypeScript, built with Vite. Tailwind CSS v4 with the design tokens in `src/styles.css`. React Aria Components for accessible primitives. No Ionic UI.
- Data lives on the device first (IndexedDB). Optional sync from version 1 through Supabase, as **encrypted records only**.
- Encryption key is derived from a user passphrase on the device with Web Crypto. The server never sees the passphrase, the key or plaintext items. A printable recovery key is offered at setup.
- AI import (paste an order, upload screenshots) goes through a Supabase edge function. It is the one place plaintext leaves the device, so it must be an explicit per-use action, send only item lines, and keep no logs or content.
- Mobile: Capacitor 8 wrapper, native barcode scanning, local notifications scheduled on the device. iOS must use CocoaPods (not Swift Package Manager), because `@capacitor-mlkit/barcode-scanning` 8.x supports only CocoaPods on iOS: add the platform with `npx cap add ios --packagemanager CocoaPods`.
- Hosting: statichost.eu (Sweden), chosen 14 Nov 2026. It applies `dist/_headers` (see `security-headers.ts`) and builds from `statichost.yml`. For now (15 Nov 2026) one site serves both the landing page at `/` and the app at `/app/`, because the free plan allows one site; revisit when a second site is available. IndexedDB belongs to the origin, not the path, so the move to `/app/` keeps existing data.
- Supabase stays the backend. Supabase is for encrypted records only, with one exception: the landing page waitlist table marketing.signup_emails, written only through public.signup_add by the signup edge function, readable by nobody else, deleted after the launch email. **Supabase project region: `eu-west-1` (Ireland), chosen by the owner on 21 Nov 2026.**
- Roadmap is 17 steps (see `docs/roadmap.md`): 1-9 web app, 10 web barcode scanning, 11-17 iOS and Android.
- Greener swaps ("Shop now" suggests eco-friendly alternatives) come from a catalogue so Claude is called rarely:
  - A bundled static catalogue keyed by product type (the item's normalised "Shelf › Subcategory"). Each entry: `key`, `label`, `tags` (e.g. refillable, plastic-free, certified), `why`, shop search-URL templates, `source`, `reviewedAt`. It contains nothing about any user.
  - The user's choice is an optional `swap` field on the item (status `accepted` | `declined` | `snoozed`, swap key, decided date, optional snooze date). It is simply part of the item, so it is encrypted and synced with it.
  - A local `swapCache` table holds results for product types the catalogue lacks. It is not user data: exclude it from export and sync.
  - Claude is called only on a catalogue miss, only after the user taps "Find another option", and only with the generic product type plus their tag choices (never brand, other items or order text), through the edge function. The reply is validated against the catalogue schema, only `https` link templates are accepted, and the result goes to `swapCache`.

## Privacy rules (hard rules)

1. The app (`src/`, served at `/app/`) may talk only to its own origin and Supabase. The landing page (`site/`, served at `/`) may also contact exactly the analytics endpoint and the sign-up service, once the owner has chosen them (`SITE_ANALYTICS_ORIGIN`, Umami Cloud's collector `https://gateway.umami.is`, and `SITE_SIGNUP_ORIGIN`, the Supabase project that runs the `signup` function, in `security-headers.ts`; never guess a provider). The landing page also loads Umami's tracker script (see rule 2). See `security-headers.ts`; keep its tests passing.
2. No third-party scripts, fonts, analytics, ad or crash SDKs, or remote images. One exception, on the landing page only and only until it is self-hosted (owner, 20 Nov 2026): Umami Cloud's tracker, loaded from its exact URL `https://cloud.umami.is/script.js` (`SITE_ANALYTICS_SCRIPT` in `security-headers.ts`), allowed by that URL in the landing page's `script-src` and in `src/site.test.ts`, and posting page views only to `SITE_ANALYTICS_ORIGIN`. Keep its `data-errors` and `data-performance` off. The app (`/app/`) never loads it.
3. Encrypt item data on the device before any upload.
4. Only `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` may reach the browser bundle. Never put a service-role key or any AI provider key in a `VITE_` variable or in the repo.
5. Never read, print or commit `.env` files. Use `.env.example` for documentation.
6. No real personal inventory in tests, fixtures, logs or screenshots. Use invented seed data.
7. Barcode lookups and any network call that reveals what a user owns must be opt-in.
8. The swap catalogue (bundled or cached) holds no user data and no affiliate links. Shop links are built from its URL templates, never taken from Claude-generated URLs.
9. `design/prototype/` is a read-only porting reference. Claude Code may read it to match behaviour, but must never edit it, copy personal data from it into the repo, or commit it. It must never be imported by app code, tests or build config.

## Design rules

The full design system lives in the owner's claude.ai Project (`shelfie/06-design-system.md`), which you cannot see. The values are mirrored in `design/tokens.json`. Treat that file as the source for colours, fonts and fixed copy. `src/styles.css` must match it: `src/design-tokens.test.ts` fails on any drift (both dark blocks included), on any extra variable, and on any colour literal outside the doc's palette in `styles.css`, `index.html`, `public/favicon.svg` or the PWA manifest. It has no exception list: do not add one to get a test passing. The PNG icons in `public/` are not checked; keep them in step with `favicon.svg`. Do not invent values, and do not edit it unless the owner says the design changed. If something you need is not in it, ask.

Rules that always apply:

- The `copy` lists in `design/tokens.json` (`must_include`, `must_not_include`) apply to the app, not the landing page (owner, 16 Nov 2026). The palette and fonts apply to both.
- Colour and type: only the palette in `design/tokens.json` and its tints. Fredoka for the wordmark and headings, Figtree for everything else. No other fonts or colours. Use the CSS custom properties (for example `var(--accent)`), never hard-coded hex values in components.
- The two main actions are named "Fill my shelves" and "Shop now". Import options use the landing page's names with Now or Planned labels, never "Coming soon".
- Mascot: the jar, with an eucalyptus body, wooden lid and cream label, and no cheeks. Its mood shows the item status.
- Voice: plain and short ("Your cupboard stays yours").
- Never show ethical ratings or labels unless a ratings source has been chosen. Do not invent ratings.
- Dark mode values are the app's own and are in the `dark` section of `design/tokens.json`.
- Fonts are bundled with the app, never loaded from a third-party CDN (privacy rule).
- `docs/design/` (create when needed) holds exported PNG/PDF screens from the design canvas, never `design/prototype/`. The canvas source files themselves are in `design/app-screens/` (see Layout).

## Commands

```sh
npm ci               # fresh checkout: installs the versions pinned in package-lock.json
npx playwright install chromium   # browser for the e2e tests
npm run dev          # local dev server
npm run typecheck    # root tsc, then src/domain again without DOM/Node types
npm run lint
npm run format       # Prettier (format:check in CI)
npm test             # Vitest unit tests
npm run test:e2e     # builds, serves with production headers, runs Playwright
npm run build        # tsc --noEmit, vite build (app to dist/app), then scripts/build-site.mjs (site/ and dist/_headers)
npm run preview      # scripts/serve-dist.mjs: all of dist/ on :4173 (/ and /app/) with the production headers
```

Single tests:

```sh
npx vitest run src/security-headers.test.ts        # one file
npx vitest run -t "only allows our own origin"     # by test name
npx playwright test e2e/foundation.spec.ts --project=desktop   # projects: desktop, phone (Pixel 7)
npx playwright test -g "theme button"
```

Versions are now resolved in `package.json` and `package-lock.json`. Use `npm ci` (or `npm install`) on a fresh checkout. Do not re-run `npm run setup`: it reinstalls every package at `latest` and bumps all the pins. Node 22+ (`.nvmrc`). CI (`.github/workflows/ci.yml`) runs lint, format:check, typecheck, unit, e2e, then `npm audit --omit=dev --audit-level=high`.

## Layout

Roadmap steps are in `docs/roadmap.md`; setup and the folder overview are in `docs/development.md`. Folders marked (planned) do not exist yet; create them in the step shown.

- `src/domain/` (step 2) pure TypeScript: item model, stock estimation, shelves, routine, import classification. No React, no storage, no network. Fully unit tested: each `x.ts` has its tests in `src/domain/testing/x.test.ts`; cross-module checks (including that domain tests run without browser globals) are in `testing/invariants.test.ts`, and shared test data in `testing/helpers/fixtures.ts` (test files only). Rules are in `src/domain/README.md`.
- `src/domain/swaps/` (planned) greener-swap catalogue, lookup and reply validation. Pure TypeScript like the rest of `src/domain/`.
- `src/storage/` (step 3) IndexedDB through Dexie, the only folder that may import `dexie` or `fake-indexeddb` (ESLint enforces it everywhere else in the repo, dynamic `import()` and `require` included). `db.ts` defines `ShelfieDB` (tables `users`, `households`, `items` storing `Item`, and `itemPurchaseRecords` storing `ItemPurchaseRecord`, one row per purchase, indexed on `itemId` and `addedAt`) and the `openDb(name?)` factory: never create a database at import time. `firstRun.ts` has `ensureLocalProfile`, which takes `now` (a `Date`) and `newId` as parameters and builds the rows with `newHousehold` and `newUser` from `src/domain`. `deleted` (on `Item`) is never indexed (IndexedDB can't index true or false), so load items by `householdId` and filter in memory. Indexed fields must be required in the type, or rows without them drop out of the index. Changing tables or indexes means adding a new Dexie version with an upgrade function; never edit version 1 once real data exists. Each `x.ts` has its tests in `src/storage/testing/x.test.ts`; they start with `import 'fake-indexeddb/auto'` and give each test its own database, deleted afterwards. `repository.ts` defines `ItemRepository`, the only way the UI (and later sync) reads and writes items, with its rules in the file's header comment; it has an in-memory version (`memory-repository.ts`) and a Dexie version (`dexie-repository.ts`), both held to one shared contract test (`testing/helpers/itemRepositoryContract.ts`, run by `memory-repository.test.ts` and `dexie-repository.test.ts`). `settings-repository.ts` defines `SettingsRepository`, built the same way for the user's and household's prefs (reads tolerant through `mergeUserPrefs`/`mergeHouseholdPrefs`, updates strict), with `memory-settings-repository.ts`, `dexie-settings-repository.ts` and the contract `testing/helpers/settingsRepositoryContract.ts`. The two interfaces and the two memory versions must not import Dexie (`src/storage-boundaries.test.ts` checks it). The `swapCache` table (excluded from export and sync) is still planned.
- `src/crypto/`, `src/sync/` (planned, step 5) encryption and Supabase sync.
- `src/ui/` (planned, step 4) React components. `src/styles.css` holds the tokens. `src/App.tsx` is currently a placeholder shell.
- **Site layout (temporary, one statichost.eu site).** The app builds with Vite `base: '/app/'` (`APP_BASE` in `security-headers.ts`) into `dist/app`, and `emptyOutDir` clears only that folder. `site/` holds the landing page, ported from `design/landing-page/landing_page_pre_launch.html` (static HTML and CSS plus two small same-origin scripts that the page works without: `site/site-assets/local-price.js` shows the Plus price in the visitor's currency from the browser language, on the device only, with fixed approximate rates; `site/site-assets/signup.js` sends the two sign-up forms with fetch and shows the result inline. Without JavaScript the forms post normally and the `signup` function redirects back to `/#signup-<form>-<result>`, which `site.css` shows with `:target`. Message wording lives only in `index.html`; `src/site.test.ts` checks that every message id the function can redirect to exists and that every form posts to `SITE_SIGNUP_ORIGIN`. E2E never contacts the real project: `e2e/site.spec.ts` answers or aborts every request to it. `site/site-assets/` holds `site.css`, the bundled Fredoka and Figtree woff2 files copied unchanged from `@fontsource-variable` with their OFL licences, copies of the mascot, leaf and icon SVGs from `design/assets/`, and the four app screenshots). Light mode only. `src/design-tokens.test.ts` checks every colour literal in `site/**/*.css` and `site/**/*.html` against the palette (hex of any length, colour functions other than `color-mix`, named colours; no `style` attributes or `<style>`), and that the fonts are byte-identical copies; `src/site.test.ts` fails on any inline script, event handler, `javascript:` URL or `<script src>` to another origin; `e2e/site.spec.ts` checks one `h1`, landmarks, images and fonts, 44px targets, no sideways scroll at 390 and 1280px, visible focus and reduced motion. `scripts/build-site.mjs` runs after `vite build`, removes anything in `dist/` other than `dist/app`, copies `site/` into the root of `dist/` and writes `dist/_headers` (app and landing page blocks; see Security headers below). The landing page's own CSS and images go in `site/site-assets/`. The PWA is scoped to `/app/`: manifest `start_url` and `scope`, the service worker at `/app/sw.js` registered with scope `/app/`, and `navigateFallback` `/app/index.html` (allow-listed to `/app/` routes). Never let it control or cache anything outside `/app/`, and do not hard-code root-relative paths in app code (use `import.meta.env.BASE_URL`). `public/` assets end up in `dist/app/`.
- `supabase/` holds the edge functions only for now; no migration files exist yet. `config.toml` came from `supabase init`; never overwrite its settings. `functions/signup/` is the landing page waitlist (`logic.ts` holds all the logic with no Deno imports and is tested by `logic.test.ts` in Vitest; `index.ts` is the Deno entry point, excluded from `tsc`, and must stay a thin wrapper). The waitlist table and function (`marketing.signup_emails`, `public.signup_add`) were created by hand by the owner and stay that way for now: do not write or change them, and do not add a `supabase/migrations/` folder for them. The encrypted-records tables and their migrations will be added when sync is built, and the AI proxy function later (steps 5-6). `supabase/README.md` describes the tables, RLS and deploy commands. Never run Supabase commands that contact or link a project: the owner deploys.
- `design/prototype/` holds the original single-file prototype, as dated downloads named `prototype-live-YYYY-MM-DD.html` (use the newest). It is gitignored and exists only on the local machine: never commit it (it may contain personal data). See hard rule 9. It is a frozen snapshot and the reference to port behaviour from, not code to ship. It is not the source for tokens or copy: see Design rules. It is about 380 KB: grep for the function you need (e.g. `calcStock`, `needsRestock`, `migrate`) instead of reading it whole. Its in-app Claude chat calls the AI directly; that must not be ported as is (AI calls go through the edge function only).
- `docs/` `decisions.md` (dated decision log; add a line when a decision changes), plus planned architecture notes, data model and privacy policy draft (see `docs/README.md`). Exported design screens go in `docs/design/` (see Design rules).
- `design/tokens.json` mirrors the design system's colours, fonts and fixed copy (see Design rules).
- `design/app-screens/` holds the screens downloaded from the claude.ai design canvas (`canvas.json`, `README.md`, and the current design in `current/phone/`, `current/web/` and `current/theme/`, files named `J-*.dc.html`). They are canvas source files, not web pages: they need the canvas's `support.js` and `{{placeholders}}`, so they don't open in a browser. Read them for markup, spacing, copy and behaviour only: never import them, never use them as the source for tokens or copy (that is `design/tokens.json`), and never copy their Google Fonts links (fonts are bundled, privacy rule 2). Prettier ignores the folder, so it stays exactly as downloaded; `README.md` there lists which file is which screen. `design/landing-page/` holds the landing page canvas downloads (`landing_page_pre_launch.html` is the current one; the copy options' defaults are the chosen wording) and their `assets/`: read-only like `design/app-screens/`, and Prettier ignores it too.
- `design/assets/` holds the static SVGs (mascot moods, one container icon per unit with `units.json`, status icons, category and privacy icons, background leaves), using only the palette and its tints, no fonts and no external references. Labelled SVGs name themselves with `aria-label` (the `<title>` repeats it as a tooltip) and contain no `id`, so the same file can be inlined any number of times on one page; the backgrounds are `aria-hidden`. Keep new SVGs to the same rules. `README.md` there says what each folder is for.

## How the pieces connect

- **Security headers are one source of truth.** `security-headers.ts` feeds `npm run preview` (`scripts/serve-dist.mjs`, a small Node static server, because `vite preview` can only serve `dist/app`) and `scripts/build-site.mjs`, which writes `dist/_headers` for statichost.eu (a path line, headers indented four spaces). It holds two sets: `appHeaders` (the strict app policy, on `/app/*`; never loosen it) and `siteHeaders` (the landing page: `default-src 'none'`, everything else `'self'` or `'none'`, so no inline scripts or styles, no `style="..."` and no `data:` URLs in `site/`). `headerRules` lists the `_headers` blocks; the landing page's are explicit paths (`SITE_PATHS`: `/`, `/index.html`, `/privacy`, `/site-assets/*`), never `/*`, because statichost.eu's handling of overlapping rules is unconfirmed: no URL may match two blocks, and nothing may rely on rule order (the unit test parses the generated file and checks sample URLs). `scripts/build-site.mjs` fails if a file in `site/` is not covered by exactly one site rule, so a new page or asset folder means adding its path to `SITE_PATHS`. The preview server uses the same rules (`rulesFor`) and answers 500 if two match. Both scripts import the `.ts` file directly, relying on Node 22's built-in type stripping, so keep `security-headers.ts` free of imports and non-erasable TypeScript (no enums). The dev server does not apply them, so CSP problems only show up in `npm run preview` and the e2e tests. The CSP is strict (`script-src 'self'`; `style-src 'self'` plus one pinned hash for React Aria's injected `#react-aria-pressable-style`): no inline `<script>`/`<style>` in `index.html` and no `style="..."` in static HTML. A React Aria upgrade that changes that style fails the e2e CSP test with the new hash; update the hash in `security-headers.ts` and its pinned test. The app's `Permissions-Policy` allows the camera only (for barcode scanning); the landing page's allows nothing. Allowing a new origin means changing `security-headers.ts` and `src/security-headers.test.ts` (which pins every directive of both policies), and asking first (privacy rule 1). `e2e/guard.ts` takes an `allowedOrigins` option: `e2e/site.spec.ts` passes `siteExtraOrigins`, everything else allows none.
- **E2E fails on any foreign request.** `e2e/foundation.spec.ts` records every request not to the app's origin and every console CSP violation. Playwright builds and previews on port 4173 (the server exits if the port is taken); `baseURL` is the origin, so tests open the app with `page.goto('/app/')` and the landing page with `page.goto('/')`. Locally it reuses an already running server, so restart a stale preview after changes.
- **`src/domain` is fenced in two ways.** ESLint (`eslint.config.js`, blocks generated per folder depth) bans imports of React, React Aria, `@supabase/*`, `@capacitor*/*`, `dexie`, `fake-indexeddb` and relative imports that climb out of `src/domain`; bans browser globals including `globalThis` and `self`; and bans `new Date()` with no arguments, `Date.now()` and `Math.random()` (today is a parameter; `new Date(value)` is fine). `src/domain/tsconfig.json` extends the root config with `"lib": ["ES2022"]` and `"types": []`, so browser and Node APIs are unknown names there however they are reached. A new subfolder deeper than three levels below `src/domain` needs another depth in `domainImportBlocks`.
- **Unit tests** only match `src/**/*.test.ts` and `supabase/functions/**/*.test.ts` in a `node` environment (no DOM, no `.tsx` tests) unless `vite.config.ts` is changed. `tsconfig.json` includes `supabase/functions` but excludes each function's `index.ts` (Deno globals and `jsr:` imports).
- **Theming.** Tokens are CSS variables in `src/styles.css`, exposed to Tailwind via `@theme inline` (`bg-surface`, `text-muted`, `border-line`, `bg-cream`). Dark values appear twice (system dark and forced `data-theme="dark"`): edit both. Theme is switched by setting or removing `data-theme` on `<html>`. Fonts come from `@fontsource-variable/*` packages, never a CDN.
- **PWA.** `vite-plugin-pwa` in `vite.config.ts` holds the manifest and Workbox precache patterns (`js,css,html,svg,png,woff2`); new asset types must be added there to work offline.
- **TypeScript/ESLint.** `tsconfig.json` lists included paths explicitly; add new top-level TS files or folders there. `verbatimModuleSyntax` plus the `consistent-type-imports` rule means type-only imports must use `import type`. `noUncheckedIndexedAccess` is on. Git and Prettier ignore `design/prototype/` (both match `prototype` at any depth), and Prettier also ignores `design/app-screens/` and `design/landing-page/`. ESLint lints only TypeScript and JavaScript, and neither folder has any.

## Conventions

- TypeScript strict. No `any`. Prefer small pure functions; keep UI thin.
- Every change to domain logic comes with tests. Estimation rules (units bought minus whole replacement periods elapsed) must stay covered.
- Items, users and households carry a `schemaVersion`, all set from the one shared `CURRENT_SCHEMA_VERSION` (`src/domain/item.ts`). Until the app is live, a model change is made in place: `schemaVersion` and the Dexie version stay at 1 and no migration is written. From launch, any model change bumps both and adds a migration.
- Accessibility: keyboard operable, visible focus, 44px touch targets, works in light and dark, respects reduced motion.
- Keep user-facing copy plain and friendly; the mascot has moods (sleepy, party, worried, happy).

## Definition of done

Typecheck, lint, format check, unit tests and e2e tests pass; no new origins contacted; docs or this file updated if a decision changed.
