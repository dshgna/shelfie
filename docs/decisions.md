# Decision log

Newest first. One line per decision, with the reason.

## Open questions

- **Does the account password also unlock the encryption key?** Supabase Auth sends the password to the server, so deriving the encryption key from it would let the server derive the key. Decide in Productionising. Until then, nothing derives a key from the account password.
- **Named device list needs its own table; decide with Productionising.** The Supabase client can't list a user's sessions, so Account settings shows only this device and "Sign out other devices".
- **TODO: the analytics and privacy switches.** Account settings links to "Analytics and privacy", which is a placeholder with the heading only until the switches are built.

Where the owner's brief named a label and the design differed, the brief's wording is used ("Keep me signed in on this device" on the web, "New to Shelfie?", "Resend email", "Export my data", the forgot-password confirmation "If that address has an account, we have sent a link."). - **The reset link opens `/app/reset-password/`.** A folder (the build copies the app's `index.html` there), so any static host serves it without a rewrite rule. Saving the new password also signs out the other devices, as the design's note says.
- **Component tests use jsdom.** `src/ui/**/*.test.tsx` files start with `// @vitest-environment jsdom` and use Testing Library with a fake `AuthService`; everything else stays in Node.
- **E2E signs in through a fake Supabase.** Playwright builds the app with `VITE_SUPABASE_URL` set to `https://e2e-fake.supabase.co` (overriding any `.env.local`), and `e2e/fake-supabase.ts` answers every request to it in the browser, so no test reaches a real project. App specs sign in first with `openSignedIn`; the auth and account specs run axe on each screen.
- **Layout and copy may be copied from `design/prototype/`.** Hard rule 9 now lets Claude Code copy screen layout, markup, spacing, copy and behaviour from the prototype files into the repo, so the sign-in and account screens can be built from `prototype-create-account-sign-in.html`. Unchanged: never edit or commit the folder, never copy personal data (use invented data), never import it, and tokens come only from `design/tokens.json`.
- **An account is required: email and password through Supabase Auth, no guest mode.** No mobile number, magic link, recovery key or two-step sign-in for now (design brief "Sign in and account", revised 26 Nov 2026). `src/auth/` holds the client, the `AuthService` (with a Supabase version), error codes and password rules. Sign-in errors use Shelfie's own wording, and a wrong password and an unknown email give the same message so accounts can't be enumerated. Account deletion needs a server function and is a later step.
- **"Keep me signed in" chooses the session storage.** On (the default), the Supabase session is kept in localStorage; off, in sessionStorage, so it ends when the app closes. The choice itself is a non-sensitive localStorage setting (`shelfie.keepSignedIn`).
- **Sign out is for this device only.** `signOut()` uses Supabase's `local` scope, so other devices stay signed in; `signOutOthers()` uses `others`. Local data stays on the device after sign-out.
- **One local database per account.** The local user id is the Supabase user id and the database is `shelfie-<userId>`, so another account signing in on the same device never sees the previous one's shelves. `ensureLocalProfile` runs only after sign-in; the household is still created on the device.

## 15 Nov 2026

- **The app and the landing page get separate security headers in one `dist/_headers`.** The app keeps its strict policy unchanged on `/app/*`; the landing page gets a tighter one (`default-src 'none'`, only `'self'` for scripts, styles, images, fonts, connections and forms, no inline code or `data:` URLs) on explicit paths (`/`, `/index.html`, `/privacy`, `/site-assets/*`), never `/*`, because statichost.eu's handling of overlapping rules is unconfirmed, so no URL may match two rules and nothing relies on their order. Privacy rule 1 now covers both: the app talks only to its origin and Supabase; the landing page may also reach exactly one analytics endpoint and one sign-up service, which stay empty placeholders until the providers are confirmed.

- **One site for now: landing at /, app at /app/. Revisit when a second site is available.** statichost.eu's free plan allows one site, so one build serves both: the app builds to `dist/app` with Vite `base: '/app/'`, and `scripts/build-site.mjs` copies `site/` into the root of `dist/` and writes `dist/_headers`, which for now applies the app's security headers to `/app/*` only. The service worker and PWA manifest are scoped to `/app/`, so they never control or cache the landing page. No root `/sw.js` cleanup was added: the owner said no old service worker at scope `/` needs removing. The Dexie database and storage are unchanged: IndexedDB belongs to the origin, not the path, so moving the app from `/` to `/app/` on the same domain keeps the data people already have. `npm run preview` is now `scripts/serve-dist.mjs`, because `vite preview` can only serve the app's own folder.

- **Settings reads are tolerant and updates are strict.** `SettingsRepository` reads prefs through `mergeUserPrefs`/`mergeHouseholdPrefs`, so a damaged or older row still gives complete, valid prefs, while an update with an invalid value or unknown key is refused and writes nothing, so bad values never get stored. The user and household rows have no timestamp and are not synced yet.

- **`ItemRepository.put` refuses to move an item between households, and `subscribe` only hears its own repository object.** A `put` whose id is already stored (even deleted) in another household rejects with `ItemHouseholdMismatchError` and writes nothing, so a bug or a bad import can't silently take an item from one household into another. Listeners hear only writes through the same repository object, so the app creates one and shares it; other repositories and other tabs will need Dexie's liveQuery or a BroadcastChannel later.

- **The UI reads and writes items only through `ItemRepository`.** One interface with an in-memory and a Dexie version that behave identically (one shared contract test), so the UI can be built before the database is wired in and storage can change without touching it. Rules: `put` stamps `updatedAt` from the clock; `remove` marks the item `deleted` instead of erasing it; `list` and `get` hide deleted items; objects are copied in and out; listeners run only after the write has committed.

- **Items carry `updatedAt` again, stamped by the repository on every save; still no `createdAt`.** Sync and conflict resolution need it to tell which copy of an item is newer and what changed since the last sync. Prototype items get the migration context's `now`. schemaVersion 1 and Dexie version 1 were changed in place, as no real data exists yet. This reverses the `updatedAt` part of the entry below.

- **`Purchase` is merged into `ItemPurchaseRecord`.** They described the same thing, so `calcStock` now takes the record's fields (`quantity`, `size`, `unit`, an optional `boughtAt` that defaults to today) plus the item's `name`, `category` and optional `lifeDays`, and rejects a quantity of 0. Import drafts use the same names (`quantity`, `boughtAt`), so the review can show the estimate before anything is saved.

- **`deleted` is on `Item`; `ItemPurchaseRecord` is one row per purchase; schemaVersion 1 and Dexie version 1 were changed in place.** Items carry `householdId` (prototype items get it from the migration context) but no longer createdAt or updatedAt, and the new `itemPurchaseRecords` table holds each purchase, ordered by `addedAt`. No real data existed yet, so neither version was bumped; from now on any change bumps them and adds a migration. (superseded 20 Nov 2026, see above)

- **Domain tests live in `src/domain/testing/`, not beside each module; shared test data in `testing/helpers/`.** Keeps the rule modules and the tests apart. The three tests in `src/` that read files (design tokens, fixture usage, security headers) stay in `src/`, outside the domain's fences.
